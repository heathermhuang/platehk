# Handoff 2026-04-20

## What changed

- Hardened the auto-update pipeline in [scripts/cron_update.sh](../scripts/cron_update.sh):
  - after refreshing source datasets, cron now also rebuilds the derived `all` dataset
  - it now regenerates the `all` preset/search artifacts before rebuilding the public API
  - this closes the gap where child datasets could update while `data/all` and `api/v1/all` stayed stale
- Expanded the integrity pass in [scripts/verify_data_integrity.py](../scripts/verify_data_integrity.py) to validate [data/all](../data/all) as a first-class dataset, not just the four child datasets
- Patched the shared-host PHP API to understand the new `all` issue identity:
  - [api/lib.php](../api/lib.php): added helpers for child dataset lists, stable dataset ordering, and parsing `all` issue selectors like `pvrm::2026-03-28`
  - [api/issues.php](../api/issues.php): `dataset=all` now returns issue metadata with `dataset_key` and `auction_key`
  - [api/issue.php](../api/issue.php): `dataset=all` now resolves `auction_key` correctly and returns rows tagged with that same key
  - [api/search.php](../api/search.php): `dataset=all&issue=<auction_key>` now filters by both dataset and date instead of assuming issue IDs are plain dates
- Added workflow coverage in [tests/test_workflows.py](../tests/test_workflows.py) so regressions in the cron chain or PHP `all` issue-key handling should fail fast

## Root cause

- The unified `all` dataset became a real build artifact on `2026-04-19`, but the cron path still reflected the older four-dataset world.
- That meant a scheduled refresh could update source JSON while leaving:
  - `data/all`
  - `data/all.*` search artifacts
  - `api/v1/all`
  out of sync with the latest source data.
- Separately, the PHP API still assumed issue selectors were always `YYYY-MM-DD`, but the new `all` contract uses `auction_key` values like `pvrm::2026-03-28`.
